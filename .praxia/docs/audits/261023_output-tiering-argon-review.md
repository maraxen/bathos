## Detailed Findings

### F-01 [BLOCKER] — Attack Surface (3): Remote GNU `mv -n` silently exits `0` without moving when destination exists
* **Citations:** [`.praxia/docs/specs/261023_output-tiering.md:175`](.praxia/docs/specs/261023_output-tiering.md#L175), [`.praxia/docs/specs/261023_output-tiering.md:205`](.praxia/docs/specs/261023_output-tiering.md#L205)
* **Defect:** Section 6.1 step 5 ([`261023_output-tiering.md:175`](.praxia/docs/specs/261023_output-tiering.md#L175)) specifies: *"On match, `ssh host mv -n …partial final` (`mv -n` never overwrites), then re-stat the final file."* On Linux (GNU coreutils `mv`), `mv -n source dest` when `dest` already exists **does not fail**—it silently skips the move, leaves `source` (`.partial`) in place, leaves `dest` untouched, and **exits `0`**. Re-statting `final` then succeeds because the preexisting `final` file is present.
* **Concrete Failure Scenario:**
  1. Two processes (or a timed-out retry and a slow background transfer, or two machines syncing the same run) both pass §6.1 step 2 (`<dest>/run-<id8>.tar.zst` does not exist yet).
  2. Writer A finishes uploading and renames `final`.
  3. Writer B (which rebuilt a local archive with a different `created_at` timestamp or different zstd stream; see **F-02**) hashes its own `.partial` in step 4, then runs `ssh host mv -n ...partial final` in step 5.
  4. `mv -n` silently does nothing and exits `0`. `stat final` succeeds.
  5. In step 6 ([`261023_output-tiering.md:176`](.praxia/docs/specs/261023_output-tiering.md#L176)), Writer B emits `output_copy.recorded` + `output_copy.verified (state=verified)` recording **Writer B's** `archive_sha256` and `manifest_sha256`, which do **not** match the bytes in `final` on the remote host, while `.partial` is orphaned forever. Subsequent `bth verify --tier outputs` fails with `corrupt_copy`.
* **Proposed Fix:** Replace `mv -n src dst && stat dst` in §6.1 step 5 with an atomic hardlink+unlink or post-move verification on the remote:
  `ln src dst && rm -f src` (POSIX `ln` without `-f` is guaranteed to fail with `EEXIST` and non-zero exit status if `dst` already exists on the same filesystem), **and** assert that ` ! -e src` holds after the rename or run step 4's `verify-file` against `final` *after* the move rather than against `.partial` before the move.

### F-02 [BLOCKER] — Attack Surface (3) & (2): Non-reproducible tar/manifest (`created_at`) breaks §6.1 step 2 idempotent resume
* **Citations:** [`.praxia/docs/specs/261023_output-tiering.md:122-123`](.praxia/docs/specs/261023_output-tiering.md#L122-L123), [`.praxia/docs/specs/261023_output-tiering.md:133`](.praxia/docs/specs/261023_output-tiering.md#L133), [`.praxia/docs/specs/261023_output-tiering.md:167-170`](.praxia/docs/specs/261023_output-tiering.md#L167-L170), [`.praxia/docs/specs/261023_output-tiering.md:205`](.praxia/docs/specs/261023_output-tiering.md#L205), [`.praxia/docs/specs/261023_output-tiering.md:244`](.praxia/docs/specs/261023_output-tiering.md#L244)
* **Defect:** Section 5.2 ([`261023_output-tiering.md:122-123`](.praxia/docs/specs/261023_output-tiering.md#L122-L123)) explicitly states: *"Byte-reproducibility is **not** promised. Identity is the manifest, not the tar bytes."* Furthermore, `run-<id8>.manifest.json` includes `"created_at": "2026-10-23T18:00:00Z"` ([`261023_output-tiering.md:133`](.praxia/docs/specs/261023_output-tiering.md#L133)), so every invocation of §6.1 step 1 ([`261023_output-tiering.md:167`](.praxia/docs/specs/261023_output-tiering.md#L167)) produces a different `manifest_sha256` and (if tar headers/zstd parameters or file mtimes vary) a different `archive_sha256`. Yet §6.1 step 2 ([`261023_output-tiering.md:168-170`](.praxia/docs/specs/261023_output-tiering.md#L168-L170)) states:
  > *"Before transferring, check whether `<dest>/run-<id8>.tar.zst` exists. If it exists with the same sha256 as the local archive, record the copy and verify it (idempotent resume). If it exists with a **different** sha256, refuse with `archive_conflict`."*
* **Concrete Failure Scenario:**
  1. `bth cold <run_id>` runs §6.1 steps 1–5: it builds a local staging archive (`archive_sha256 = H1`, `created_at = T1`), uploads it to the primary `cold` host, and renames it to `<dest>/run-<id8>.tar.zst`.
  2. Before step 6 emits `output_copy.recorded` (or mid-mirror before `--mirror` finishes, the exact test case in Step 6 at [`261023_output-tiering.md:244`](.praxia/docs/specs/261023_output-tiering.md#L244)), the process is killed (`SIGINT`/SSH drop) and the temporary local staging dir is cleaned up or recreated on rerun.
  3. The operator re-runs `bth cold <run_id>`. Step 1 builds a fresh local archive (`archive_sha256 = H2`, `created_at = T2`).
  4. Because byte-reproducibility is not guaranteed (`H2 != H1`) and `manifest.json` has `T2 != T1`, step 2 sees `<dest>/run-<id8>.tar.zst` on the remote with `H1 != H2` and **refuses with `archive_conflict`**, permanently wedging the run unless the user manually SSHes in to delete the remote cold archive.
* **Proposed Fix:** Either:
  1. **Make the archive & manifest deterministic** (sort tar members lexicographically, normalize tar header `mtime=0, uid=0, gid=0, uname="", gname=""`, pin zstd level/threads, and remove `created_at` from `manifest.json` or set it to `reference_event.ts`); **or**
  2. **Change §6.1 step 2 idempotent resume** to fetch `<dest>/run-<id8>.manifest.json` from the remote when `<dest>/run-<id8>.tar.zst` already exists: if the remote manifest's `files` array (`[{relpath, size_bytes, sha256}]`) equals `reference_hashes(run_id)` AND `myxcel cold verify-file` confirms the remote `.tar.zst` matches the remote manifest's `archive_sha256` + `archive_size_bytes`, adopt those remote hashes and emit `output_copy.recorded` + `output_copy.verified` without re-uploading.

### F-03 [BLOCKER] — Attack Surface (3): Two-file split (`run-<id8>.tar.zst` + `.manifest.json`) crash window and broken multi-source `rsync` invocation
* **Citations:** [`.praxia/docs/specs/261023_output-tiering.md:89`](.praxia/docs/specs/261023_output-tiering.md#L89), [`.praxia/docs/specs/261023_output-tiering.md:168-177`](.praxia/docs/specs/261023_output-tiering.md#L168-L177)
* **Defect:** Cold storage writes two sibling files (`run-<id8>.tar.zst` and `run-<id8>.manifest.json`), but §6.1 steps 2–5 only track and verify `.tar.zst`:
  1. Step 3 ([`261023_output-tiering.md:171`](.praxia/docs/specs/261023_output-tiering.md#L171)) specifies: `rsync --partial-dir=.bth-partial <archive> <manifest> host:<dest>/run-<id8>.tar.zst.partial`. Passing **two** source files (`<archive>` and `<manifest>`) to `rsync` with a single destination path (`.../run-<id8>.tar.zst.partial`) causes `rsync` to treat `run-<id8>.tar.zst.partial` as a **directory** and create `run-<id8>.tar.zst.partial/run-<id8>.tar.zst` and `run-<id8>.tar.zst.partial/run-<id8>.manifest.json` inside it!
  2. Steps 2, 4, and 5 ([`261023_output-tiering.md:168-175`](.praxia/docs/specs/261023_output-tiering.md#L168-L175)) never check, verify, or atomically rename `run-<id8>.manifest.json.partial -> run-<id8>.manifest.json`.
* **Concrete Failure Scenario:**
  1. Even if uploaded separately, suppose `run-<id8>.tar.zst.partial` is renamed to `run-<id8>.tar.zst` in step 5, and the SSH connection drops before `run-<id8>.manifest.json` is uploaded/renamed.
  2. On retry, step 2 ([`261023_output-tiering.md:168-169`](.praxia/docs/specs/261023_output-tiering.md#L168-L169)) checks only whether `<dest>/run-<id8>.tar.zst` exists, sees a matching sha256, records the copy as `verified`, and exits `0`—leaving `run-<id8>.manifest.json` completely missing on the remote. Later, `bth warm <run_id>` ([`261023_output-tiering.md:90`](.praxia/docs/specs/261023_output-tiering.md#L90)) fails because it needs the manifest to verify extracted files.
* **Proposed Fix:**
  1. Transfer each file to its own `.partial.<attempt_uuid>` path (or embed `manifest.json` as the first member inside `run-<id8>.tar.zst` in addition to the sibling sidecar).
  2. Upload, verify (`verify-file`), and atomically link/rename `run-<id8>.manifest.json` **first**, and only then rename `run-<id8>.tar.zst` (so the presence of final `run-<id8>.tar.zst` is the single commit point).
  3. In step 2 (idempotent resume) and in `bth verify --tier outputs` ([`261023_output-tiering.md:91`](.praxia/docs/specs/261023_output-tiering.md#L91)), verify **both** `run-<id8>.manifest.json` (`manifest_sha256`) and `run-<id8>.tar.zst` (`archive_sha256`, `archive_size_bytes`).

### F-04 [BLOCKER] — Attack Surface (4): Contradiction between §4 and D5 on `adopt`, plus post-run drift laundering across `fold_runs.py`, `claim.py` (AC-20), and `readback.py`
* **Citations:** [`.praxia/docs/specs/261023_output-tiering.md:67-68`](.praxia/docs/specs/261023_output-tiering.md#L67-L68), [`.praxia/docs/specs/261023_output-tiering.md:88`](.praxia/docs/specs/261023_output-tiering.md#L88), [`.praxia/docs/specs/261023_output-tiering.md:208`](.praxia/docs/specs/261023_output-tiering.md#L208), [`.praxia/docs/specs/261023_output-tiering.md:266-267`](.praxia/docs/specs/261023_output-tiering.md#L266-L267), [`src/bathos/runlog/fold_runs.py:474-477`](src/bathos/runlog/fold_runs.py#L474-L477), [`src/bathos/claim.py:1300-1305`](src/bathos/claim.py#L1300-L1305), [`src/bathos/readback.py:143-175`](src/bathos/readback.py#L143-L175), [`src/bathos/readback.py:214-250`](src/bathos/readback.py#L214-L250)
* **Defect:** Three interlocking defects in the `run_end` vs `adopted` design:
  1. **Direct Spec Contradiction (§4 vs §3.2/§7/D5):**
     - Section 4 ([`261023_output-tiering.md:88`](.praxia/docs/specs/261023_output-tiering.md#L88)) states `bth outputs adopt` **Refuses when:** *"A `run_end` already exists for that path with a different hash."*
     - Section 3.2 ([`261023_output-tiering.md:68`](.praxia/docs/specs/261023_output-tiering.md#L68)), Section 7 ([`261023_output-tiering.md:208`](.praxia/docs/specs/261023_output-tiering.md#L208)), and Decision D5 ([`261023_output-tiering.md:266-267`](.praxia/docs/specs/261023_output-tiering.md#L266-L267)) state: *"When the latest rebaseline differs from `run_end`, tiering refuses with `outputs_drifted` until `bth outputs adopt` records a new reference."*
     If `adopt` refuses whenever a `run_end` exists for that path with a different hash (§4), then D5's recovery path (`Run bth outputs adopt if intentional`, [`261023_output-tiering.md:208`](.praxia/docs/specs/261023_output-tiering.md#L208)) will **always refuse**!
  2. **Post-Run Drift Laundering into `runs.output_metadata`:**
     [`fold_run`](src/bathos/runlog/fold_runs.py#L474-L477) folds `runs.output_metadata` by taking the latest `run.outputs_hashed` event regardless of `phase`:
     ```python
     outputs_events = by_kind.get("run.outputs_hashed", [])
     if outputs_events:
         latest = max(outputs_events, key=lambda ev: (ev.get("ts", ""), ev.get("eid", "")))
         row["output_metadata"] = _as_json_text(latest.get("data", {}).get("output_metadata"), default="[]")
     ```
     Because `bth outputs adopt` emits `run.outputs_hashed` with `"phase": "adopted"` ([`261023_output-tiering.md:88`](.praxia/docs/specs/261023_output-tiering.md#L88)), `fold_run` overwrites `runs.output_metadata` with the `adopted` hashes.
  3. **Defeating AC-20 Parity Gate & Trust-Ledger Provenance:**
     - [`parity_confound_check`](src/bathos/claim.py#L1300-L1305) checks `output_metadata_has_sha_drift(output_metadata_json)` on `runs.output_metadata` to downgrade a `literature_parity` run to `"uncontrolled"` if its verdict artifacts were mutated on disk after the run (AC-20).
     - [`resolve_pin`](src/bathos/readback.py#L143-L175) and [`_find_run_with_output_sha256`](src/bathos/readback.py#L214-L250) read `runs.output_metadata` to determine whether an artifact was genuinely produced by `run_id` (`ProductTrustState.CANDIDATE`) and whether it is `fresh`.
* **Concrete Failure Scenario:**
  1. An operator or agent runs a confirmatory or `literature_parity` script; `run_end` hashes `outputs/verdict.json` (`sha256 = AAA`). Or the script wrote `outputs/extra.parquet` without declaring it in `[outputs] roots`.
  2. After the run finishes, the operator edits `outputs/verdict.json` (or fabricates `outputs/extra.parquet` by hand) and runs `bth outputs adopt <run_id> --root outputs/`.
  3. `bth outputs adopt` emits `run.outputs_hashed (phase: adopted)` with `sha256 = BBB`.
  4. [`fold_run`](src/bathos/runlog/fold_runs.py#L474-L477) overwrites `runs.output_metadata` with `BBB`. Now [`parity_confound_check`](src/bathos/claim.py#L1304) sees zero drift (`BBB == BBB`), [`get_trust_state`](src/bathos/readback.py#L297) certifies the hand-edited file `BBB` as a run-produced `CANDIDATE`, [`resolve_pin`](src/bathos/readback.py#L166) reports `fresh=True`, and `bth cold` archives the tampered file as a verified run output.
* **Proposed Fix:**
  1. **Enforce §4's immutability rule strictly:** `run_end` hashes are immutable provenance. If a path already has a `run_end` hash, `bth outputs adopt` **must never** overwrite it (remove the claim in D5 / §7 `:208` that `adopt` can override a drifted `run_end` hash; if a `run_end` output was intentionally mutated post-run, it is no longer the output of `<run_id>` and must be produced by a new run).
  2. **Scope `adopt` strictly to unrecorded paths/legacy runs:** `bth outputs adopt` may only add paths that have **no** `run_end` hash, and its `"phase": "adopted"` provenance must be preserved per-entry (`"phase": "adopted"`) inside `output_metadata`.
  3. **Protect AC-20 and `readback.py`:** In [`fold_runs.py:474-477`](src/bathos/runlog/fold_runs.py#L474-L477), never let a `rebaseline` or `adopted` event overwrite a `run_end` entry's `sha256`, and in [`claim.py:1304`](src/bathos/claim.py#L1304) and [`readback.py:150,248`](src/bathos/readback.py#L150), require `entry.get("phase", "run_end") == "run_end"` for confirmatory parity and trust-ledger candidate eligibility.

### F-05 [BLOCKER] — Attack Surface (6) & (1): Changing `output_metadata` key `"path"` → `"relpath"` and assuming project-relative paths breaks existing consumers
* **Citations:** [`.praxia/docs/specs/261023_output-tiering.md:37`](.praxia/docs/specs/261023_output-tiering.md#L37), [`.praxia/docs/specs/261023_output-tiering.md:60-62`](.praxia/docs/specs/261023_output-tiering.md#L60-L62), [`.praxia/docs/specs/261023_output-tiering.md:120-121`](.praxia/docs/specs/261023_output-tiering.md#L120-L121), [`.praxia/docs/specs/261023_output-tiering.md:240`](.praxia/docs/specs/261023_output-tiering.md#L240), [`src/bathos/runner.py:1302`](src/bathos/runner.py#L1302), [`src/bathos/runner.py:1495-1500`](src/bathos/runner.py#L1495-L1500), [`src/bathos/runner.py:1641`](src/bathos/runner.py#L1641), [`src/bathos/compact.py:143-195`](src/bathos/compact.py#L143-L195), [`src/bathos/checker.py:223-248`](src/bathos/checker.py#L223-L248), [`src/bathos/query.py:64`](src/bathos/query.py#L64), [`src/bathos/readback.py:150,249,605`](src/bathos/readback.py#L150), [`src/bathos/mcp.py:4218,4314`](src/bathos/mcp.py#L4218)

  1. **False assumption in §5.2 (`:120-121`):** The spec claims `output_metadata` already uses paths *"relative to the project root"*. Here, `output_copy.recorded` carries creation metadata (`run_id`, `tier`, `profile`, `host`, `path`, `archive_sha256`, `archive_size_bytes`, `manifest_sha256`, `reference_phase`, `reference_event_eid`, `config_layer`, `recorded_at`), whereas `output_copy.verified` is emitted later by `bth verify --tier outputs` ([`261023_output-tiering.md:91`](.praxia/docs/specs/261023_output-tiering.md#L91)) to update `state` and `verified_at`. If `fold_output_copies.py` simply takes the latest event per `copy_id`, `output_copy.verified` lacks the `NOT NULL` columns from `output_copy.recorded` (`config_layer`, `reference_phase`, `reference_event_eid`, `recorded_at`) and either fails the `NOT NULL` constraint on `INSERT` or overwrites them!
  2. **Same-millisecond tie-break inversion in §6.1 step 6:** In §6.1 step 6 ([`261023_output-tiering.md:176`](.praxia/docs/specs/261023_output-tiering.md#L176)), `bth cold` emits `output_copy.recorded` (`state="unverified"`) and `output_copy.verified` (`state="verified"`) back-to-back in the same Python process. Look at [`src/bathos/runlog/writer.py:92-121`](src/bathos/runlog/writer.py#L92-L121): `_uuid7()` uses millisecond timestamp + 74 random bits (`os.urandom(10)`), and `_utc_now_iso()` has millisecond resolution. Two events emitted within the same millisecond have **identical `ts` and identical top 48 bits of `eid`**, so their `(ts, eid)` sort order is determined by **random bits (`rand_a`, `rand_b`)** (`50%` chance `output_copy.recorded` sorts *after* `output_copy.verified`, leaving the copy stuck in `state='unverified'`!).
* **Concrete Failure Scenario:**
  1. `bth cold <run_id>` completes §6.1 step 5 and in step 6 calls `emit_event("output_copy.recorded", ...)` followed immediately by `emit_event("output_copy.verified", ...)` within the same millisecond.
  2. With 50% probability, `_uuid7()` gives `output_copy.recorded` a larger random suffix in `eid` than `output_copy.verified`.
  3. `fold_output_copies.py` sorts by `(ts, eid)`, picks `output_copy.recorded` as the latest event, and sets `state = 'unverified'` and `verified_at = NULL`. Immediately thereafter, Step 6's acceptance test (`bth cold` followed by `--mirror` preemption check at [`261023_output-tiering.md:179-181`](.praxia/docs/specs/261023_output-tiering.md#L179-L181)) sees no `verified` copy and re-transfers the archive from scratch!
* **Proposed Fix:**
  1. Fold `output_copies` by **merging** per `copy_id` in chronological order: latest `output_copy.recorded` populates the base record (`run_id`, `tier`, `profile`, `host`, `path`, `archive_sha256`, `archive_size_bytes`, `manifest_sha256`, `reference_phase`, `reference_event_eid`, `config_layer`, `recorded_at`), and latest `output_copy.verified` (whose `ts >= recorded.ts`) updates `state` and `verified_at`.
  2. Even simpler: allow `output_copy.recorded` itself to carry `state="verified"` and `verified_at` when §6.1 step 4 already verified the file before step 6, eliminating the redundant back-to-back event emission in step 6.

### F-13 [MAJOR] — Attack Surface (2): `copy_id = sha256(run_id|tier|profile|path)[:16]` omits `host`, causing cross-machine `warm` collisions and `cold`/`mirror` split-brain

* **Defect:** Section 5.3 ([`261023_output-tiering.md:146`](.praxia/docs/specs/261023_output-tiering.md#L146)) defines `copy_id = sha256(run_id|tier|profile|path)[:16]`.

### F-20 [MAJOR] — Attack Surface (3) & (5): Concurrent `bth cold` `.partial` clobber and `rsync` mtime/size skip on corrupted `.partial` retry

* **Defect:**
  1. **Fixed remote `.partial` name (`run-<id8>.tar.zst.partial`):** Because §6.1 step 3 ([`261023_output-tiering.md:171`](.praxia/docs/specs/261023_output-tiering.md#L171)) uses a static `.partial` filename per run rather than a per-attempt token (and also passes `--partial-dir=.bth-partial` on top of an explicit `.partial` suffix), two concurrent `bth cold` processes for the same run overwrite the same remote `.partial` file between step 4 (hash check) and step 5 (rename)—a classic TOCTOU window where Writer A verifies `.partial`, Writer B truncates `.partial` to start its upload, and Writer A renames the truncated `.partial` to `final`!
  2. **`rsync` skip on corrupted `.partial` retry:** Section 6.1 step 6 ([`261023_output-tiering.md:176-177`](.praxia/docs/specs/261023_output-tiering.md#L176-L177)) states: *"On mismatch: leave the `.partial` in place, emit `failed`, and exit non-zero.   1.On step 4 hash mismatch, **delete** the corrupt remote `.partial` file (or pass `--ignore-times` / `--checksum` to `rsync`).
  2. Include a per-invocation unique suffix in the staging filename during step 3→4→5 (or delete `--partial-dir=.bth-partial` if the target is already named `.partial`, using `rsync --partial --inplace` to `run-<id8>.tar.zst.partial` for resumable single-writer uploads and a remote `flock` / lockfile `<dest>/.lock` to serialize concurrent writers).
