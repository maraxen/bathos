# Brainstorm: Abstraction boundary + open design questions for productizing the `literature-parity` validation workflow as a reusable cross-project bathos epic workflow (+ /using-bathos skill section + claim-tier `[confounds.reference_parity]` wiring)

## Problem Frame
FIXED CONSTRAINTS (cannot change):
1. The orchestrator — not the in-workflow agents — owns the runnable-test re-derivation lock. A verdict is never trusted on agent assertion alone; decisive findings must be re-derived by runnable synthetic-ground-truth tests (tests/test_*_invariants.py) executed by the orchestrator. This holds wherever the seam falls.
2. The 5-phase skeleton (blind reconstruction xN -> reconcile -> adversarial refutation xM -> adjudicate -> graded verdict) is validated and load-bearing; we are settling its abstraction boundary and parameters, not replacing it.
3. Blindness is sacred in Phase 1: reconstructors see source-of-truth ONLY (no code, no prior summary, no peers). This anti-laundering property is the source of the value.
4. Redundancy is mandatory (a single reader laundering one set of errors IS the failure mode). N>=2, M>=2 minimum; exact counts are negotiable.
5. The verdict is graded (PARITY / PARTIAL / FAIL), not binary — mirroring /jax-port's graded posture.
6. The workflow must emit durable, auditable artifacts: clause checklist + verdict + invariant tests.
7. Claim-tier integration mirrors register-before-runs: the `[confounds.reference_parity]` block cannot be marked `controlled` until a passing parity run exists; `parity_run_id` must point at a real run.
8. bathos owns standard writes; this ships as a named workflow + /using-bathos skill section + bth CLI/MCP surface — implementable, not pure research.

NEGOTIABLE (the divergence surface):
A. Seam placement: how thin/fat the engine is vs the plugin/config (the abstraction-boundary tension).
B. Invariant-test authoring locus: workflow phase (agent authors) vs orchestrator step (orchestrator authors) — given the lock (execution) stays with the orchestrator either way.
C. Redundancy economics: fixed N,M vs scale-to-complexity vs loop-until-no-new-defects.
D. Mode A/B detection + how Mode A composes with (vs duplicates) /jax-port.
E. Reproduce-protocol graceful-degradation ladder + its honest labeling.
F. bth gating shape: CLI/MCP surface, where the gate fires, how parity_run_id is bound.
G. Artifact format/location/durability mechanism.
H. Paper-ambiguity surfacing mechanism.

CENTRAL FRAMING QUESTION (lock this): "Where do we draw the domain-agnostic engine / domain-specific plugin seam so the literature-parity workflow is reusable across asr, bathos, and future projects WITHOUT leaking domain assumptions (invariant KINDS, metric semantics, the reproduce-protocol's direction-of-effect notion) into the engine — while keeping the orchestrator-owned runnable-test lock intact regardless of where the seam falls?"

## Idea Pool
- [ai] A1 — Thin-engine / fat-plugin seam (invariant-kind registry): The engine owns ONLY the domain-agnostic 5-phase orchestration, the RECON/CHECKLIST/REFUTE/ADJ/VERDICT JSON schemas, the lens-fanout machinery, the grading rubric (PARITY/PARTIAL/FAIL), and the orchestrator-owned runnable-test lock. Everything domain-specific — the invariant KINDS (marginal preservation, detailed balance, root-correctness), the metric semantics, and the direction-of-effect notion — lives behind a registered plugin interface: a project ships an `invariants.py` exposing a typed catalog of invariant-kind generators. The engine never names a domain concept; it only calls `plugin.candidate_invariants(checklist)` and `plugin.reproduce_protocol(verdict)`.
- [ai] A2 — Fat-engine / thin-config seam (prompt-template + args): Assumption-reversal of A1. The engine carries a rich library of domain-agnostic PROMPT TEMPLATES and reconstruction/attack lenses, and the only domain-specific surface is a declarative `parity.bth.toml` args file (paper_pdf, impl_paths, citation_note, recon_lenses, attack_lenses, hypotheses, equivalence_bound). No code plugin at all — the 'domain' enters purely as natural-language args the agents read. The invariant KINDS are emitted by the agents themselves at verdict time as a generated test spec, never pre-catalogued. Maximally portable (zero per-project code) at the cost of less type-safety on invariant kinds.
- [ai] A3 — Two-seam (compiler/runtime) split: A middle path that names TWO seams instead of one. Seam-1 (engine/IR): the engine compiles paper+code into a domain-neutral Intermediate Representation — a 'clause graph' of typed assertions (each clause = {claim_text, code_locus, verdict_enum, evidence_refs}). Seam-2 (IR/domain): a domain adapter interprets clause types into invariant-test stubs. The agents and the lock both operate on the IR, so the engine is domain-blind by construction and the domain adapter is a pure IR->pytest transformer. Makes the invariant KIND a property of a clause's TYPE in the IR, not of the engine.
- [ai] A4 — Capability-probe seam (engine asks, project answers): Rather than a static plugin registry (A1) or pure args (A2), the seam is a set of ORCHESTRATOR CALLBACKS the engine invokes at defined phase boundaries: `can_run_reference_code()`, `list_on_disk_systems()`, `propose_invariant_for_clause(clause)`, `score_direction_of_effect(result)`. The project implements whichever callbacks it can; unimplemented callbacks degrade gracefully (e.g., no on-disk systems -> protocol-only reproduction). The engine's domain-agnosticism is enforced by the callback INTERFACE being the only channel through which domain knowledge enters — and Mode A/B detection becomes just 'is can_run_reference_code() implemented and truthy'.
- [ai] B1 — Orchestrator-authors (replicate worked instance): The verdict phase emits an invariant-test SPEC (a structured description of each decisive invariant: name, the synthetic ground truth to construct, the assertion, the expected pass/fail signature). The orchestrator then writes and runs the actual pytest file. Agents never touch executable code; they only produce the spec. Maximum control, hardest to game — matches exactly what caught the Zeinaty defect. Cost: the orchestrator is a bottleneck and must understand the domain enough to translate spec->test.
- [ai] B2 — Agent-authors-then-orchestrator-re-derives (split authorship from lock): A dedicated workflow phase has an agent WRITE the invariant test file (it has domain context the orchestrator may lack), but the LOCK is preserved by the orchestrator independently re-deriving the decisive numeric finding via its own minimal assertion — i.e., the agent's test is treated as untrusted UNTIL the orchestrator reproduces its key number with a separate one-line check. Authorship scales (agent does the verbose part); trust stays orchestrator-side. Distinct from B1 in WHO writes the bulk test code.
- [ai] B3 — Adversarial test authorship (refuter writes, reconstructor must pass): Assumption-reversal: make test authoring itself adversarial. The refutation agents (Phase 3) author candidate invariant tests DESIGNED to fail against our code (each refuter encodes its alleged defect as a runnable test). The orchestrator runs them; a test that the refuter expected to fail but passes exonerates that clause, a test that fails confirms the defect. The invariant suite is thus the by-product of the adversarial phase, not a separate verdict step — and the orchestrator's lock is just 'execute the adversaries' tests.'
- [ai] C1 — Fixed 3+3 floor (replicate the decisive instance): Hard-code N=3 reconstructions, M=3 refutations as the default, exactly as validated (~760k tokens / ~17 min was decisive). Predictable cost, predictable coverage; the redundancy floor is a constant the user can trust. Override only downward with an explicit `--cheap` flag that the verdict records as a reduced-rigor caveat.
- [ai] C2 — Scale-to-complexity (paper-budget heuristic): N,M scale with a cheap up-front complexity estimate of the paper/method (e.g., # of distinct algorithmic clauses extracted in a pre-pass, or # of hyperparameters, or page count of the methods section). A 1-page method gets 2+2; a 12-clause method gets 4+4. The engine computes the budget; the verdict records the chosen N,M and the complexity signal that drove it.
- [ai] C3 — Loop-until-no-new-defects (saturation stopping rule): Run reconstructions/refutations in waves; stop when a full wave surfaces zero NEW distinct clauses/defects beyond those already in the checklist (saturation), subject to a hard ceiling (e.g., max 6 of each) and the N>=2/M>=2 floor. Spends tokens proportional to the actual ambiguity/defect density rather than a guessed complexity. Verdict records the saturation curve (defects-per-wave) as evidence the search was exhausted.
- [ai] C4 — Severity-triggered escalation (cheap-default, deepen-on-hit): Start at the 2+2 floor; escalate redundancy ONLY on the clauses where the first pass found a DEVIATION or AMBIGUOUS verdict. Clean clauses stay at floor coverage; suspect clauses get extra independent refuters focused narrowly on them. Decouples breadth (one cheap pass over everything) from depth (concentrated firepower where signal appeared). Verdict records per-clause coverage, not a global N,M.
- [ai] D1 — Mode A delegates wholesale to /jax-port (engine calls the skill): When reference code is published, the literature-parity engine does NOT reimplement numeric diffing — it invokes /jax-port's graded-parity skill as a sub-step and ingests its graded result as the Mode-A evidence channel. literature-parity owns only the clause-checklist framing around it. Zero duplication; /jax-port stays the single source of truth for impl-vs-impl numeric parity. Risk: coupling to /jax-port's interface/availability.
- [ai] D2 — Unified evidence-channel model (Mode A/B are channels, not modes): Reframe: there is one workflow with four pluggable EVIDENCE CHANNELS — (i) clause-level text-parity, (ii) adversarial-refutation survival, (iii) invariant-test pass, (iv) protocol reproduction — and a fifth optional channel: numeric impl-diff (the /jax-port-style check) that is simply AVAILABLE when code is published. 'Mode A vs B' dissolves into 'which channels have evidence.' The verdict grades on the union of available channels; code-published just unlocks the numeric channel. Avoids a hard mode-switch and makes partial-code cases (some modules published) first-class.
- [ai] D3 — Detection by manifest declaration, not auto-sniff: The orchestrator declares mode explicitly in the args/manifest (`reference_code: <path|null>`), rather than the engine auto-detecting code availability. Honest and deterministic: the human/orchestrator asserts whether published code exists and is trustworthy (a repo that is a stale prototype is worse than no code). Auto-sniffing a repo risks treating a fork/demo as the reference. The verdict records the declared provenance of the reference artifact.
- [ai] D4 — Mode A as cross-check on Mode B, never a substitute (assumption-reversal): Reverse the default that code-published is the easy/strong path. Even when code exists, ALWAYS run the blind text-only Mode B reconstruction, then use the published code purely as an independent CROSS-CHECK against the text reconstruction (does the code match what the paper says?). This catches papers whose published code DIVERGES from their own text — a real failure class. Mode A becomes an additional adversarial witness, not a shortcut that skips the blind phases.
- [ai] E1 — Explicit reproduction-fidelity ladder (typed rungs): Codify graceful degradation as a fixed enum of fidelity rungs the verdict MUST select from: R0 exact (paper's systems+metrics reproduced on disk, quantitative match) > R1 metric-substituted (same systems, proxy metric) > R2 protocol-faithful (different on-disk systems, same procedure, qualitative direction-of-effect) > R3 invariant-only (no reproduction; parity rests on text+refutation+invariant tests) > R4 unreproducible (verdict capped at PARTIAL). The chosen rung is a required, durable field and mechanically caps the max grade (e.g., R2 cannot yield full PARITY, only PARITY-with-caveat). Direction-of-effect 'success' is defined per-rung, so the engine never hardcodes a domain's notion of 'effect.'
- [ai] E2 — Direction-of-effect as a plugin-supplied predicate: The notion of 'the paper's effect reproduced qualitatively' is domain-specific, so the engine takes a plugin-supplied `direction_of_effect(result) -> {confirmed, contradicted, inconclusive}` predicate. The engine only orchestrates calling it and recording the outcome; the project owns what 'the effect went the right way' means. Keeps the reproduce-protocol phase domain-blind. Pairs naturally with the A1/A4 seam choices.
- [ai] E3 — Substitute-system registry with honesty tax: When the paper's exact systems are absent, the orchestrator picks substitute on-disk systems from a declared registry, and the verdict applies an automatic 'honesty tax' — it records BOTH (a) what was reproduced (substitute systems, qualitative direction) and (b) what was NOT reproduced (the exact quantitative claim), and the `[confounds.reference_parity]` block is marked `controlled-by-protocol` rather than `controlled`, a strictly weaker status that downstream claim-tier gating treats as partial. Makes the degradation legible to the Union Gate, not just to a human reading prose.
- [ai] F1 — `bth parity` first-class subcommand family (mirror `bth claim`): Introduce a sibling of the claim-tier CLI: `bth parity scaffold <reference>` (writes a parity.bth.toml from the paper), `bth parity validate`, `bth parity run` (executes the workflow, runs the invariant tests, emits the verdict artifact + a parity run record), and `bth parity register --campaign <id>` which binds the resulting `parity_run_id` into the campaign's `[confounds.reference_parity]` block and flips status uncontrolled->controlled ONLY if the run passed. MCP mirrors (parity_scaffold/validate/run). Symmetric with the claim-tier mental model the user already trusts.
- [ai] F2 — Reuse the run+sidecar machinery (parity is just a tracked run with a special outcome): No new subcommand family. The parity validation is a script in scripts/validation/ with a sidecar whose outcome conditions encode PARITY/PARTIAL/FAIL as DuckDB SQL over the verdict JSON. `bth run` tracks it like any experiment; the resulting run_id is what the campaign's `[confounds.reference_parity].parity_run_id` points at. Gating is enforced at `bth campaign conclude`: the Union Gate is extended to check that any confound with a reference_parity sub-block has a parity_run_id whose run outcome='pass'. Minimal new surface; maximal reuse of existing tiered-catalog + Union-Gate plumbing.
- [ai] F3 — Gate at submit-time, not conclude-time (fail fast): Assumption-reversal of F2's conclude-time gate. Mirror the reproduction-prerequisite gate already in `bth submit`: a confirmatory run whose campaign has an uncontrolled reference_parity confound is HARD-BLOCKED at submission (hard exit for validation/production tiers, advisory for exploration/calibration). Forces parity to be established BEFORE the expensive confirmatory campaign burns cluster time, rather than discovering at conclude that the baseline was never validated. Pairs with F1 or F2 for the establish-parity half.
- [ai] F4 — Parity as a claim CONFOUND lifecycle, no separate object: Fold parity entirely into the existing claim-tier. The `[confounds.reference_parity]` sub-block already exists; add a `bth claim attest-parity <campaign> --run <parity_run_id>` verb that validates the cited run is a real passing parity run and stamps an audit event (SHA-anchored like claim register). Sprint-audit gains a Signal (e.g. Signal 13): 'confirmation campaign cites a published-method baseline but reference_parity is uncontrolled / parity_run_id empty / cited run not a parity run.' No new top-level command tree — parity lives as a first-class confound state machine inside claims.
- [ai] G1 — Three-artifact bundle, content-addressed, catalog-pinned: The workflow emits a fixed triple — (a) clause checklist (JSON, the IR), (b) graded verdict (markdown audit doc, human-facing), (c) invariant test file (pytest, the lock). All three are SHA256-hashed and pinned into the parity run record's output_paths; the verdict's SHA is what `parity_run_id` ultimately authenticates. Re-running with drifted code/paper changes the hashes, so a stale parity claim is mechanically detectable (mirrors claim-tier's SHA tamper-anchor + bth check git-drift gate). Durable, auditable, drift-aware.
- [ai] G2 — Living pytest gate as the primary artifact (test IS the doc): Assumption-reversal of G1's doc-centric bundle. The DURABLE artifact is the invariant pytest file checked into tests/, and the verdict markdown + checklist are merely generated reports DERIVED from it. The parity claim stays alive because the test runs in CI on every commit — parity isn't a one-time audit, it's a standing regression gate. If the reimplementation drifts, the invariant test breaks the build. Trades one-shot auditability for continuous enforcement; the catalog stores a pointer to the test, not a frozen verdict.
- [ai] G3 — Artifacts as internal-docs convention + bathos sidecar (split human/machine): Human-facing verdict goes to .praxia/docs/audits/YYMMDD_<paper>-parity-verdict.md (matches the worked instance and the internal-docs convention); the machine-facing checklist + invariant-test-result JSON go into the bathos catalog as the parity run's result + output_paths. The two are cross-linked by run_id. Respects the existing docs taxonomy (audits/) AND the catalog as separate-but-linked stores, rather than inventing a new bundle format.
- [ai] H1 — Ambiguity as a first-class checklist verdict that propagates: AMBIGUOUS is not collapsed into MATCH/DEVIATION at reconcile; it survives all the way to the verdict as an explicit caveat with the competing readings recorded ({clause, reading_a, reading_b, which_our_code_chose, impact_if_wrong}). An unresolved AMBIGUOUS clause that is load-bearing mechanically caps the grade at PARTIAL — you cannot claim full PARITY against a paper you had to guess about. Forces underspecification into the open instead of silently picking.
- [ai] H2 — Reconstruction-disagreement as the ambiguity SIGNAL (no separate detector): Use the divergence ACROSS the N blind reconstructions as the mechanical detector of paper ambiguity: any clause where reconstructors disagreed is auto-flagged ambiguous-candidate; agreement = paper was clear (or all misread identically — itself a recorded risk). The engine needs no domain knowledge to detect ambiguity; it just diffs reconstructions. The verdict reports the disagreement matrix as evidence. Cheap, domain-blind, and directly exploits the redundancy that already exists.
- [ai] H3 — Ambiguity escalates to a human/orchestrator decision gate: Unresolved load-bearing ambiguities are not auto-resolved by the workflow at all — they are surfaced as an explicit decision queue the orchestrator (or human) must rule on before the verdict finalizes, each ruling recorded with its rationale and stamped into the audit doc. The workflow refuses to emit a full-PARITY verdict while the queue is non-empty. Trades automation for honesty: the workflow will not paper over an underspecified method, it stops and asks.
- [ai] X1 — Grading as a mechanical cap-lattice, not a judgment call: The PARITY/PARTIAL/FAIL grade is COMPUTED, not adjudicated: each evidence dimension (clause-parity %, adversarial-survival, invariant-tests-pass, reproduction-rung, ambiguity-load) imposes a CEILING on the grade, and the final grade is the min over ceilings (e.g. any FAIL invariant test -> FAIL; any load-bearing AMBIGUOUS or reproduction-rung worse than R1 -> max PARTIAL). Removes grader discretion and makes the verdict reproducible from the artifact alone. The domain only supplies which clauses/invariants are 'load-bearing.'
- [ai] X2 — 'Invariant-kind' as a shared cross-project LIBRARY, not per-project plugin: Orthogonal to the seam question: ship a growing bathos-owned catalog of GENERIC invariant kinds that recur across domains (marginal/measure preservation, detailed balance / reversibility, monotonicity-under-signal, ablation-nullification, permutation/relabeling invariance, conservation, rank-correlation preservation). Projects pick from the shared library and only author truly novel kinds locally. The 'domain-specific' surface shrinks over time as the library captures recurring kinds — the seam MOVES as the library grows. Reframes the abstraction boundary as evolutionary rather than fixed.
- [ai] X3 — Skill-only, zero-engine MVP (assumption-reversal of 'productize the engine'): Reverse the premise that we need a code engine at all for v1. Ship literature-parity purely as a /using-bathos SKILL SECTION ('Validating a reimplemented baseline') — a documented protocol an orchestrator follows by hand, plus the parity.bth.toml schema and the F2 conclude-gate. No workflow-engine code; the redundancy/lenses/lock are enforced by the skill's checklist and the human/orchestrator. Lowest implementation cost, fastest to ship, defers the engine/plugin seam decision until a second project actually needs it (avoids premature abstraction from N=1 worked instance).
- [user] Ready to converge. Cognitive-forcing beat first — the biggest risk of the leading architecture: ABSTRACTION-FITTING TO A SAMPLE OF ONE. Only two properties of the Zeinaty worked instance are actually validated and load-bearing — (1) blindness (Phase-1 reconstructors see the source-of-truth ONLY) and (2) the orchestrator-owned runnable-test lock (the decisive number is re-derived, never asserted). Everything else — the 3+3 redundancy count, the math/algo/protocol lens triple, the reproduce-protocol's direction-of-effect notion, and above all the engine/plugin SEAM — is plausible scaffolding never exercised against a second domain. Building a code engine with a frozen plugin interface now pays full abstraction tax against N=1: the second project will need a callback we didn't anticipate, forcing an engine fork or a contorted project. This risk is what drives the leading choice toward a skill-protocol spine with only an irreducible code minimum, deferring the seam until a second domain demands it.

## Decision Log
- [MERGE] X3 — Skill-only zero-engine MVP (as the v1 SHIP target): [CRITIC] axis=meta-tension lens=feasibility,reversibility,cost finding=X3 wins the v1 ship boundary because the only N=1-validated invariants are blindness (Phase 1 source-only) and the orchestrator-owned runnable-test lock — both enforceable by a skill protocol at zero engine cost, while the seam decision is genuinely unknowable until a second domain exercises it. But X3 alone under-specifies the durable surface, so MERGE: X3 is the engine-deferral decision, carrying the F2 conclude-gate + parity.bth.toml schema + the cap-lattice (X1) as the only CODE we build now. severity=INFO. The merge target is 'skill-protocol + thin-config + mechanical gate', not 'pure prose'. This is the architecture spine.
- [ACCEPT] Axis A (seam): A2 fat-engine/thin-config (parity.bth.toml args) — chosen; A1/A3/A4 deferred: [CRITIC] axis=A lens=feasibility,reversibility,cost finding=A2 is the correct seam for v1 because it draws the domain boundary at a declarative TOML args file (paper_pdf, impl_paths, recon_lenses, attack_lenses, equivalence_bound) with ZERO per-project code — the agents read domain knowledge as natural-language args and emit invariant KINDS at verdict time. severity=INFO. A1 (typed plugin registry), A3 (two-seam IR/compiler), A4 (callback probe) all freeze an interface against N=1; A3 especially is FATAL-on-cost (a clause-graph IR + IR->pytest transformer is a compiler project, disproportionate to a 17-min worked instance). A2 is maximally reversible: when a second project needs type-safety, you graduate specific args into A4 callbacks WITHOUT rewriting the engine. A2 is the seam that lets X2 (shared library) and A4 emerge evolutionarily rather than being guessed now.
- [REJECT] Axis A rejected: A3 two-seam compiler/IR split: [CRITIC] axis=A lens=cost,feasibility finding=A3 builds a domain-neutral clause-graph IR plus a pure IR->pytest domain adapter — i.e. a two-stage compiler — to productize a single 17-minute worked instance. severity=MAJOR (cost). The IR is an attractive abstraction but it is the textbook premature-generalization trap: you cannot design a correct typed-clause IR from one paper's clause shapes, and a wrong IR is worse than no IR (it forces every future domain to lie in its vocabulary). The runnable-test lock does NOT need an IR — it needs a number to re-derive. Reject for v1; revisit only if X2's shared invariant library independently grows enough typed kinds to make an IR fall out naturally.
- [DEFER] Axis A deferred: A4 capability-probe callback seam: [CRITIC] axis=A lens=reversibility finding=A4's callback interface (can_run_reference_code, propose_invariant_for_clause, score_direction_of_effect) is the RIGHT eventual seam — it's the graduation target from A2 — but committing to the callback signatures now repeats the N=1 freeze error. severity=INFO. Defer A4 as the documented evolution path: A2 args that recur across the first 2-3 real projects get promoted to A4 callbacks. Mode A/B detection collapses cleanly to 'is can_run_reference_code implemented' in A4, which is why D3 (manifest declaration) is the v1 stand-in. Keep A4 in the spec as the named next-seam.
- [MERGE] Axis B (invariant-test authoring locus): MERGE B2-as-default + B1-as-floor; B3 rejected: [CRITIC] axis=B lens=feasibility,edge-case,user-impact finding=The lock (Constraint 1) fixes EXECUTION at the orchestrator regardless; the only open question is who writes the bulk test code. MERGE B2+B1: default to B2 (agent authors the verbose test from its domain context, orchestrator independently RE-DERIVES the decisive number with its own minimal one-line assertion = the trust boundary), with B1 (orchestrator authors the whole spec->test) as the mandatory FLOOR for the single decisive finding. severity=INFO. This is exactly what the Zeinaty instance did — agents claimed, orchestrator's 4/4 test confirmed. Edge case B2 covers that B1 alone bottlenecks: the orchestrator may lack domain context to author the verbose suite, but it always can re-derive ONE number. The merge keeps authorship scalable and trust orchestrator-side.
- [REJECT] Axis B rejected: B3 adversarial test authorship (refuter writes the suite): [CRITIC] axis=B lens=edge-case,feasibility finding=B3 makes the invariant suite a by-product of refuters encoding alleged defects as runnable tests. Elegant, but it has a FATAL coverage gap: a refuter that fails to imagine the defect writes no test for it, so the suite's completeness is bounded by adversarial imagination rather than by the decisive-finding checklist. severity=MAJOR. The Zeinaty mechanism-nullification was confirmed by a targeted invariant the orchestrator chose to re-derive, not by an adversary's pre-written failing test. B3 also muddies the lock: 'execute the adversaries tests' trusts the adversary's test construction, which is the laundering risk Constraint 1 exists to prevent. Keep adversarial refutation as a PHASE (it stays), but not as the authoring locus for the locked suite. Fold B3's good idea — refuters propose candidate invariants — into B2 as input, not as the authority.
- [MERGE] Axis C (redundancy economics): MERGE C1 floor + C4 severity-triggered escalation; C2 rejected, C3 deferred: [CRITIC] axis=C lens=cost,user-impact,edge-case finding=MERGE C1+C4: hard floor at the validated 3+3 (C1 — the N=1 decisive cost, ~760k tokens/17min, a number the user can trust) for breadth, then C4 severity-triggered escalation concentrating extra refuters ONLY on clauses that came back DEVIATION/AMBIGUOUS. severity=INFO. This decouples cheap breadth (one pass over everything) from deep firepower (where signal appeared) and records per-clause coverage. Reject C2 (scale-to-complexity): the complexity proxy (#clauses, page count) is an unjustified numeric heuristic — exactly the threshold-cutoff skepticism the project memory flags; clause count doesn't predict defect density. Defer C3 (loop-until-saturation): the saturation stopping rule is the principled long-term answer but needs the cap-lattice and per-wave defect telemetry to exist first; revisit once C4's per-clause coverage data accumulates.
- [REJECT] Axis C rejected: C2 scale-to-complexity paper-budget heuristic: [CRITIC] axis=C lens=edge-case finding=C2 sets N,M from a cheap up-front complexity proxy (clause count, hyperparameter count, methods-section page count). severity=MINOR. The proxy is an unjustified cutoff: defect density does NOT track page count — the Zeinaty defect was a single mathematically-invariant readout wiring, a one-clause method that would have been under-budgeted by a page-count heuristic.
